# Forest Chopper — архитектура

> **Актуальная карта реализации (2026-11-01).** Это описание текущего кода, а не проект будущего движка.
> Для целей и правил игрового опыта см. [GAME_DESIGN.md](GAME_DESIGN.md),
> для конкретных механик — [GAME_MECHANICS_CATALOG.md](GAME_MECHANICS_CATALOG.md).
> При расхождении с этим текстом проверяйте исходники и тесты.

## 1. Система в целом

Forest Chopper — статическое веб-приложение из нативных ES-модулей JS и отдельный
Python WebSocket-сервер. Сборщик и React не требуются; Three.js и GLTFLoader
загружаются через CDN. Игрок может играть без Python-сервера (offline) или
присоединиться к общему серверному миру (online).

```text
index.html / index_debug.html
  └─ src/main-menu.js + main-menu-state.js + main-menu.css
       ├─ localStorage: метаданные сохранения, настройки, недавние серверы
       ├─ /status: разовый WebSocket-запрос, не создаёт игрока
       └─ динамический import(src/main.js) только по команде «Играть»
            ├─ Three.js: renderer / scene / camera / GLB / GPU-ресурсы
            ├─ ctx: общая точка доступа к модулям и состоянию игры
            ├─ world.js, terrain.js, distant-forest.js, micro-grass.js
            │    └─ WorldTaskScheduler → world-stream-worker.js
            ├─ player.js: requestAnimationFrame / движение / отрисовка
            ├─ controls.js, pickup-interaction.js, inventory-ui.js
            ├─ offline-save.js / progress.js / day-cycle.js
            ├─ multiplayer.js ─ WebSocket или PeerJS bridge
            │                     └─ forest_server.py (серверный мир)
            └─ world-startup.js: загрузочный overlay на этапе заполнения мира
```

Публичный `index.html` **не** создаёт `window.__gameDebug`; он доступен только
в `index_debug.html` после запуска игры. Другие точки входа — инструменты
редактирования 3D в `characters/humanoid/`, не часть главного меню.

## 2. Жизненный цикл и границы состояний

1. **Меню.** Не создаются Three.js/WebGL-контекст, игровые объекты и worker-ы.
   `src/main-menu-state.js` читает существующий offline-save, но не загружает мир.
   `src/settings.js` позволяет сохранять графические параметры до создания renderer.
2. **Выбор режима.** `continue` восстанавливает сохранение,
   `new` задаёт seed 0–999998 и сбрасывает прошлый локальный мир,
   `online` настраивает сервер/P2P. Параметры запуска передаются в
   `globalThis.__forestLaunch` с резервной записью в `sessionStorage`.
3. **Загрузка модулей.** `src/main.js` создаёт scene, renderer, общие геометрии,
   модель персонажа и игровые системы, после чего запускает frame loop.
4. **Готовность.** `src/world-startup.js` держит экран загрузки минимум 3 и
   максимум 5 секунд **после начала рендеринга**: ожидаются 5×5 ближайших
   детальных чанков (или меньшая область на Low), 3×3 тайла рельефа, начальная
   трава, первая партия дальнего леса и подключение в online. Успешная готовность
   должна стабилизироваться 350 мс. Ограничение в 5 секунд исключает зависание;
   дальние чанки могут продолжить появляться после перехода.
5. **Игра.** `src/player.js` ведёт `requestAnimationFrame`, физику, анимацию
   и кадры renderer. Мировые чанки обновляются инкрементально.
6. **Выход в меню.** Offline-save сбрасывается на диск браузера (если доступно),
   сетевой клиент отключается, затем `location.reload()`. Освобождение ресурсов
   WebGL выполняет браузер, а не сложный ручной teardown всех модулей.

Нельзя переносить создание renderer/воркеров в начальную загрузку меню:
это нарушит его лёгкую точку входа и предварительное применение MSAA.

художественный pipeline и готовую игровую интеграцию.

## 4. Процедурный мир и GPU

- Мир состоит из 24-метровых детальных лесных чанков. Рельеф стримится
  более крупными тайлами (в текущем коде 96 м).
- Истинная высота грунта для коллизий вычисляется аналитически; renderer
  получает worker-сгенерированные сетки. Изменения seed/параметров должны
  отменять устаревшие результаты.
- Дальний лес объединяется в независимые 96-метровые сектора GPU Instancing;
  frustum culling выполняет Three.js.
- Трава использует отдельные near/far LOD и пул InstancedMesh.
- Пресеты графики объявлены в `src/performance-presets.js`: Ultra/High
  используют MSAA, Medium/Low — без MSAA. Изменение антиалиасинга требует
  нового WebGL-контекста; остальные поддерживаемые параметры применяются
  через настройки/пересоздание нужных батчей.
- Для геометрии и кешей действуют бюджеты; ручная проверка производительности
  на Intel iGPU/NVIDIA остаётся важной даже при зелёных unit-тестах.

## 6. Сеть: точки входа и время

- Прямое подключение к Python `websockets` по `ws://` или `wss://`
  (для страницы по HTTPS нужен WSS).
- `/status` — отдельный одноразовый WebSocket-путь: отвечает
  `server_status` с `online`, `max_players`, `world_seed`,
  `world_created_at`, `day_phase`, `protocol_version:1`; **не**
  создаёт участника и не занимает слот. На старых серверах может отсутствовать.
- `/bots` — отдельная точка для headless-ботов с собственной моделью доступа.
- Основной WebSocket начинает с `welcome`. Сервер проверяет рубку,
  сбор/подбор предметов, инвентарь, постройки, чат и общее состояние.
  Успешное действие подтверждается серверным событием; локально не следует
  оптимистично считать его завершённым.
- Рубка дерева больше не увеличивает `wood` автоматически: сервер
  сохраняет `fallen_logs` в `boxes` с `item:{id:'log',count:3}`,
  `mask:0b111`, `direction`, `tree`, `expires_at:time+3600`, отправляет
  `tree_fell` с направлением, затем `box_add`.
  Ствол становится видимым только после удаления анимированного дерева
  (`FALL_DURATION=5/1.3 ≈ 3.846 с`); сервер запрещает преждевременный подбор по `ready_at`.
  `src/fallen-log-layout.js` рассчитывает постоянные центры трёх
  3,6-метровых сегментов по исходным индексам, `InstancedMesh` рисует
  только сегменты с установленными битами. `pickup_box` отправляет
  `id` контейнера **и `segment`**, сервер проверяет расстояние до
  конкретного сегмента и отдаёт одно бревно. `box_add` после успешного
  подбора содержит прежнюю геометрию, но меньшее `mask`/`count`;
  на последнем бревне — `box_remove`, плюс личный `inventory_state`. Сервер остаётся единственным арбитром при
  одновременном подборе несколькими игроками.
- `fallen_logs` и обычные выброшенные коробки имеют одинаковый TTL
  3600 секунд от создания. После истечения срока сервер удаляет связку
  целиком (`box_remove` подписанным через AOI клиентам), офлайн-клиент удаляет её локально.
  Подбор отдельного сегмента **не продлевает** срок остальных сегментов.
  Старые offline/server saves без `mask`/`direction` читаются с
  восстановленным непрерывным набором индексов; старый `expires_at:0`
  один раз мигрирует в TTL 1 час, сохранение сразу перезаписывается, чтобы
  перезапуск не обнулял таймер. Деревья в `felled` не восстанавливаются.
- PeerJS — сигнализация/транспортный мост, а **не** источник игрового состояния.
- Время суток: `day_phase` приходит в `welcome`, затем `time_sync`
  примерно каждые 10 секунд. Клиент экстраполирует между пакетами;
  сервер хранит абсолютную эпоху дня. Цикл — 16 минут.
- Онлайн-игрок получает своё временное состояние инвентаря/vitals;
  долговременное сохранение **общего мира** и постоянный персональный аккаунт
  — разные вещи. Системы аккаунтов в проекте нет.

Если меняется сетевой пакет, ID ресурса или save-схема — синхронизировать
Python/JS и добавить проверки совместимости.

### Коллизии создаваемых построек
- `src/structure-collisions.js` — общий слой столкновений с пользовательскими постройками. Структуры регистрируют локальные AABB-боксы в `group.userData.collisionBoxes` вместе с `collisionRadius`; они преобразуются в мировые координаты с учётом четырёх ориентаций. Не требуется физический движок и отдельное тело для каждой детали.
- `src/crafting.js` автоматически создаёт коллайдеры для всех деревянных элементов процедурной скамейки непосредственно из их реальных размеров и поворотов. Спинка и подлокотники сделаны тоньше; не добавляются «пустые» сплошные коллайдеры там, где геометрии нет. Данные не сериализуются отдельно: при загрузке offline/online мира коллайдеры восстанавливаются вместе с моделью.
- `src/physics.js`: проверка горизонтального блокирования с учётом высоты ног и головы, подшаги от туннелирования при длинном шаге, поддержка приземления на сиденье/перемещения по нему, последующего прыжка и схода, пересечения с потолком при прыжке снизу. Уже существующие коллизии установленных брёвен и скал сохранены.
- При демонтаже/удалении скамейки её коллайдер исчезает вместе с моделью. Следующие виды построек смогут подключиться к общему механизму посредством тех же данных `collisionBoxes`, без добавления отдельной системы физики.


### Два FPS-счётчика (рендер и физика)
- `src/player.js`: `animate(now)` вызывается через `requestAnimationFrame` по расписанию браузера; физика, root motion, игровые обновления и анимации выполняются перед `createFrameLimiter.allow()`. `dt=clamp((now-lastTime)/1000,0,0.05)`; отдельного fixed timestep нет.
- `src/settings.js`: `tickPhysics(now)` вызывается на каждом валидном rAF-кадре, независимо от ограничения частоты рендера; `tick(now,ctx)` считает только разрешённые кадры рендера. Оба счётчика независимо усредняются примерно раз в секунду и отображаются как `Render FPS` / `Physics FPS`.
- Фактический `Physics FPS` обычно близок к частоте обновления дисплея (60/120/144/165 Гц), но браузер может ограничивать его при нагрузке, неактивной вкладке или энергосбережении. `Render FPS` ограничивается настройкой maxFps и производительностью GPU/CPU. Сбор статистики отключён при выключенной панели и не сохраняется на сервер.


### Диагностика CPU/GPU Frame Time
- **CPU Frame Time**: `src/player.js` оборачивает весь игровой вызов `animate` замерами `performance.now()`, включая симуляцию, подготовку сцены и вызов `renderer.render()` для разрешённых рендер-кадров. На кадрах, пропущенных FPS-лимитером, измеряется только логика. `src/settings.js` усредняет все rAF-вызовы приблизительно раз в секунду. Это *wall-clock* время выполнения JS-кода, а не чистое CPU utilization (включает возможное ожидание браузера/драйвера внутри вызовов WebGL).
- **GPU Frame Time**: `src/gpu-frame-timer.js` запускает таймер `EXT_disjoint_timer_query_webgl2` (WebGL2) либо `EXT_disjoint_timer_query` (WebGL1) вокруг части `animate`, выполняющей рендеринг/теневые проходы. GPU-сэмплирование — не чаще одного запуска за 250 мс, не более одного запроса в полёте; результаты читаются исключительно при `QUERY_RESULT_AVAILABLE`, без блокирующих `gl.finish`/`readPixels`. При `GPU_DISJOINT_EXT` замер отбрасывается, при отсутствии расширения панель показывает «н/д».
- **Интерпретация**: CPU-время отображает среднее по всем rAF-циклам (включая кадры без рендера при его ограничении); GPU-время относится только к выбранным отрисованным кадрам, и эти величины не суммируются в полное время кадра. Измерения включаются только при активной FPS-панели, не изменяют ограничители и не отправляются на сервер.


### Дневной и ночной профиль освещения (2026-11-02)
- Клиентские настройки: src/settings.js → вкладка **💡 Освещение**. Все значения сохраняются в существующем forest-chopper:settings:v1 в localStorage, не входят в сохранение мира и не меняют серверный протокол.
- Диапазон яркости дневного солнца **0–5**, яркости костра/факела (день и ночь) с 1–10 до **1–100**. Шаг сохранён для дробных малых значений; значения по умолчанию изменены отдельным профилем дня/ночи. Изменяется только интенсивность источников, не радиус, число источников или бюджет теней.
- src/lighting-profile.js: 16 игровых часов. 0–4 и 12–16 — дневной профиль; 4–6 — плавное затемнение (smoothstep), **6–10 глубокая ночь**, 10–12 — плавный рассвет. Сервер по-прежнему синхронизирует только фазу времени.
- src/day-cycle.js смешивает дневные и ночные значения освещения: defaults день ambient=1.2/sun=2.0; ночь ambient=0/moon=0.2. Ночное небо затемнено до #010203, зенит #000101. Цвет тумана плавно приближается к чёрному #000000; ночное зрение меняет освещение, не цвет неба. При остановке цикла ночной режим рельефа сбрасывается.
- src/terrain.js: дальность ночью 30 м по умолчанию (ползунок 30–160 м). Во время ночи меняется camera.far, плотность тумана и фактический радиус загружаемых terrain-чанков; панорама озёр отключается, независимо от их размера. Возврат к дневной видимости плавный.
- src/distant-forest.js использует ту же ограниченную дальность для instanced дальних деревьев и worker-секторов; ночная дальность не расширяется озёрами.
- `src/micro-grass.js` дополнительно ограничивает **видимый радиус мелкой травы 30 м в глубокой ночи**, независимо от дальности ночной видимости, если пользователь поставит её выше 30 м. В сумерки `effectiveGrassRadius()` плавно интерполирует дневную настройку к `min(дневная дальность травы, 30)`, радиус округляется до метра во избежание постоянных изменений LOD. `syncLayer` убирает ненужные InstancedMesh-страницы из сцены (реально снижает draw calls/число треугольников), а не только прячет их в шейдере. При изменении только радиуса страницы, оставшиеся в зоне, не перегенерируются; сэмплы удалённых страниц сохраняются в 20-МБ LRU для восстановления днём. Генератор, плотность и дневной ползунок травы не меняются.
- Старый дефолт ночной видимости 60 м мигрирует к 30 м в localStorage однократно; отдельно выставленные значения ночной видимости сохраняются. Ночные значения радиуса костра и факела остаются 30 м; дневные радиусы без изменений.
- Пресеты графики теперь используют **100%** контрастность теней по умолчанию; в настройке разрешения карт направленных теней доступно **4096×4096 (4K)** дополнительно к 512/1024/2048. Для локального point-light cubemap огня остаётся 256×256 на грань, чтобы не выделять 6 карт 4K.
- При обновлении старого localStorage значения, совпадающие с предыдущими дефолтами, автоматически мигрируют; пользовательские значения, отличающиеся от старых дефолтов, сохраняются. Ползунок дневного солнца ограничен 5. Дневные регулировки работают даже при выключенной смене суток.
- src/atmosphere.js: при глубокой ночи отключаются карты теней для дерева/построек/персонажа от направленного света Луны (опция nightDisableMoonShadows), однако видимая модель Луны и её слабое освещение остаются. При рассвете тени автоматически возвращаются.
- src/campfire-model.js, src/camp-structures.js и src/landmarks.js: яркость день/ночь 1–100, радиус динамических/общих теней 1–30 м, независимые радиус освещения 10–250 м и дальность отключения лампы 10–250 м (оба default 100), затухание decay 0–3 (default 2) и высота 0.2–4 м. В ночном профиле по умолчанию яркость костра/факела 30, радиус динамических теней 30 м. Все построенные огни в пределах дальности активации освещают сцену плюс стартовый костёр, тени огней доступны в течение всего дня и ночи.
- Источники для огненных теней днём и ночью выбираются общей функцией selectFireShadowSources() из src/fire-shadow-policy.js: N ближайших подходящих огней, **включая стартовый костёр** в том же бюджете, не N плюс стартовый. Бюджет N=0–4, по умолчанию 2; максимум N кубических карт теней × 6 проходов (до 24 shadow passes на отрисованный кадр при N=4), что может ощутимо влиять на FPS; остальные огни показывают кэшированные тени без покадровых обновлений. На Low или при отключении чекбокса огненных теней не будет.
- Обычная вкладка **Освещение**: новый ползунок **лимита источников с обновляемыми тенями 0–4** (`fireShadowLimit`, default 2, шаг 1), применяется без перезагрузки и сохраняется в localStorage; отдельный чекбокс `fireShadows` остаётся глобальным выключателем. Лимит управляет только количеством покадровых обновлений карт, а не количеством видимых источников или кэшированных теней; высокий лимит может повысить GPU Frame Time. Лунное освещение по умолчанию **0.2** (ночной ambient всё ещё 0); миграция для сохранённого прежнего дефолта 0 выполняется один раз, отличающиеся значения сохраняются.
- **Одна карта на источник:** старый режим разделения удалён. Для костра/факела один PointLight с полной яркостью и одна общая кубическая карта всех объектов. Для солнца только две карты CSM по дальности, каждая со всеми caster-типами, отдельной карты персонажей нет.
- **Выкл:** только один активный источник света на костёр/факел, и один направленный солнечный свет (вторые источники скрываются/не влияют на сцену), с полной исходной яркостью и **общей** картой статических и динамических caster-объектов, пересчитываемой каждый отрисованный кадр. Восстановление режима не требует перезагрузки. В точечном режиме это 6 граней shadow cubemap на каждый огонь в лимите; в разделённом — 6 динамических граней каждый кадр и 6 статических граней лишь при необходимости (на первом/инвалидированном кадре — до 12 проходов на один логический огонь). Переключатель не меняет формат сохранений мира.

- **Про "в фоне"**: CPU выбор geometry/casters можно готовить в worker, но GPU shadow render на текущем WebGL-контексте выполняется во время рендеринга. Первым шагом стоит распределять пересчёт граней/карт между кадрами (и инвалидировать только при перемещении источника/изменении окружения), а не обещать бесплатный Web Worker GPU render.
- Два независимых переключателя: shader flame (деформируемые конусы против legacy-конусов), additive billboard glow вокруг огня. Реальный PointLight не зависит от этих переключателей.
- Только в `index_debug.html` и только **offline** доступен чит «⏸ Заморозить время суток». `createDayCycle.setFrozen(true, now)` захватывает точную текущую фазу в `phaseAt()` (её используют освещение, небо и аудио), остаётся на месте даже после нескольких циклов; debug-ползунок продолжает менять фазу во время заморозки. `setFrozen(false, now)` возобновляет ход времени с зафиксированной фазы без скачка. При переходе в online заморозка сбрасывается, серверный `time_sync` не затрагивается.
- Тестирование: scripts в tests/lighting-profile.test.mjs, tests/day-cycle.test.mjs, tests/terrain-visibility.test.mjs, tests/distant-forest.test.mjs, tests/settings.test.mjs. В debug offline выставить 0/5/6/8/10/11/12 часов, осмотреть костёр, факел, лес и дальний берег озера.

### Оптимизация наземного лута: instancing, пространственный индекс и AOI (2026-11-01)

Вместо двух независимых мешей на каждый предмет в сцене используются два возможных `InstancedMesh` на активный пространственный чанк 24×24 м: коробки (один куб/инстанс) и сегменты брёвен (один существующий log-меш/инстанс). Фреймовая логика видимости активирует чанки возле игрока на радиусе 85 м, фрустум-каллинг пропускает чанки за камерой. Грязные чанки перестраиваются с бюджетом не чаще 500 мс; содержимое далёких чанков остаётся в модели без GPU-объектов. Рендеринг в упрощённых JS-тестовых THREE-моках сохраняет прежний fallback.
- **Поиск и TTL клиента:** `src/ground-box-index.js` индексирует каждую коробку и каждый лежащий сегмент по координатам в ячейках 24 м; `pickupCandidates` получает только ближайшие ячейки, после чего **сохраняет** существующий тест достижимости 2,8 м и проекцию на экран прицела (это экранный отбор, не Three.js Raycaster). Min-heap по `expires_at` позволяет на каждом tick проверять только ближайший срок; повторные частичные обновления сегмента не перезапускают TTL, устаревшие элементы кучи игнорируются по версии.
- **TTL и AOI сервера:** `box_registry.py` — совместимый с dict `BoxRegistry`, который поддерживает индекс ячеек, min-heap истечения и обновления индексов при записи в словарь. `forest_server.py` не сканирует все 10 000 коробок для TTL. У каждого клиента `visible_boxes` с 120-метровой зоной интереса. `welcome` содержит только актуальный лут поблизости, при перемещении на 12 м пересчитывается подписка и отправляются delta `box_add`/`box_remove`; изменения и истечение TTL рассылаются только подписанным клиентам. Коробки далеко от игроков **всё равно** истекают по серверным часам, хранятся в общем мире и сохраняют один и тот же срок.
- **Диагностика:** только в `index_debug.html` доступен `__gameDebug.lootStats()` со счётчиками логических коробок и активных instanced draw batches. Тесты проверяют 1000 коробок в одной ячейке, раздельный подбор сегментов, TTL и AOI.

### DEBUG single-player save benchmark (2026-11-02)

- `src/offline-save.js` exposes `restoreSnapshot(raw,{replace:true})`; DEBUG suspends normal save writes before loading this snapshot to guarantee that the player's world on disk survives the test. The live world is cleared, terrain/forest is regenerated from the saved seed, box objects restored and position/camera teleported.
- `src/debug.js` offers `loadBenchmarkSave()`, `benchmarkBoxes(enabled)`, `startBoxBenchmark(options)`, `benchmarkStatus()` and `exitBenchmark()`. Same loaded location is measured twice, without and with the boxes, with a warmup and a settling period.

### Ragdoll и экран смерти (2026-11-02)
- `src/ragdoll.js` содержит общую физику для смерти, сна и ручного Ragdoll в обычной игре, физический движок загружается динамически с `esm.sh/@dimforge/rapier3d-compat@0.20.0` при первой смерти, сне либо нажатии обычной кнопки Ragdoll. Клиент не загружает Rapier до этого события и не требует сборки.
- **Единый lifecycle камеры ragdoll:** `src/player.js:createRagdollCameraLifecycle` сохраняет режим вида при входе, включает третье лицо для показа тела, уменьшает `camera.near` и сбрасывает сглаживание орбиты. На выходе восстанавливает предыдущий вид (включая первое лицо), `near=0.1` и сбрасывает pivot камеры, чтобы следующий кадр следовал уже за реальной позицией игрока. `src/ragdoll.js` вызывает `ragdollCamera.enter()` после успешной активации и `ragdollCamera.exit()` из **единого `ragdoll.reset()`**. Поэтому `ragdoll-controls.getUp`, пробуждение с кровати, `death.respawn` (offline и online), `death.restore`, отменённая загрузка/поздняя инициализация используют одно восстановление. Не добавлять особые camera-reset ветки в death/bed/DEBUG; новые пути должны вызывать общий `ragdoll.reset()`. `death.respawnAt` отдельно устанавливает новые координаты и направление аватара, но не управляет состоянием камеры.
- Система из 11 capsule collider + **ограниченных шарниров** создаётся по world-позам костей `SkinnedMesh`; торс закреплён fixed-joint, руки, колени, бёдра и шея имеют анатомически ограниченные revolute-joints с мягким pose-restoring PD motor. Локальные joint frames калибруются по исходной позе, чтобы ограничения не выворачивали конечности при активации. Коллайдеры столкнутся с поверхностью и друг с другом, кроме непосредственно соединённых сегментов. Solver работает с 12 итерациями; фиксированный треугольный terrain collider строится из реальных `terrain.heightAt` вокруг игрока. Каждую физическую итерацию world-позы кости переводятся обратно в локальные относительно родительской кости. В `src/player.js` при активном `ctx.ragdoll` пропускаются анимационные/двигательные обновления локального персонажа, но world renderer продолжает работать.
- `reset()` восстанавливает локальные позиции/quaternion костей и систему анимаций без reload. Ни авторитетный online мир, ни offline save не изменяются.
- **Передача кинематики:** `src/ragdoll-motion.js` измеряет через `createPlayerMotionTracker` фактическое смещение игрока после Root Motion и коллизий (м/с) и угловую скорость поворота камеры (рад/с). При активации `ragdoll.trigger()` **до асинхронной загрузки WASM** фиксирует текущие X/Z скорости, `verticalSpeed` прыжка/падения и yaw rate, затем задаёт их всем 11 rigid bodies через `setLinvel/setAngvel`. Нажатия клавиш больше не нужны: внешняя физика сама развивает ускорение от гравитации (19 м/с²), контактов и шарниров. Сопротивление воздуха `linearDamping=1.25` плюс трение о землю/объекты убирает вечное скольжение. Для сна начальная скорость намеренно нулевая. После вставания/телепорта трекер сбрасывается, чтобы перемещение на респавн не становилось ложным импульсом.
- **Единый Collision World:** `src/collision-world.js` — единственный источник описания физически твёрдых препятствий. Он читает живые объекты из `ctx.placed`, `ctx.trees`, `ctx.rockColliders`, `ctx.crafting.items`, `ctx.campStructures.items`, `ctx.storages.structures` и получает формы `capsule` для брёвен, `cylinder` для стволов/камней, локальные `box` построек и высоты рельефа. Позиции, радиусы, ориентации и высоты задаются здесь; адаптеры не хранят собственных размеров препятствий. Формат engine-neutral; новая постройка регистрирует `group.userData.collisionBoxes`, новая категория препятствий добавляется только сюда.
- **Kinematic adapter:** `src/collision-kinematic.js` преобразует формы единого мира в проверки занятости, препятствий, высоты опоры и потолка. `src/physics.js` использует этот адаптер для прежнего пошагового движения X/Z, плавного скольжения вдоль стен, прыжков, падения и подъёма с ragdoll. Обычная ходьба не создаёт Rapier-мир; модуль/WASM заранее загружается при входе в мир для будущего ragdoll. `rock-collisions.js` и `structure-collisions.js` сохранены только как совместимые функции старых модулей/тестов и тоже используют примитивы Collision World, не определяют собственную геометрию.
- **Rapier adapter:** `src/ragdoll-colliders.js` создаёт `RigidBodyDesc.fixed` + `ColliderDesc.capsule/cylinder/cuboid` и terrain trimesh из **того же самого** `collisionWorld.collect`. Локальный участок радиусом 25 м обновляется при перемещении таза на 9 м и при `collisionWorld.invalidate()` от живых изменений мира. Установка/удаление брёвен, скамей, сундуков/стеллажей, постройка/снос других объектов, рубка дерева, генерация/выгрузка чанков, загрузка сохранения и сетевые сообщения инвалидируют общий revision, чтобы у Rapier не оставались призрачные коллайдеры. Кровать при сне регистрирует матрас один раз вместо второго набора деталей.
- Различается **способ обработки** одних и тех же примитивов (кинематическое блокирование/выбор опоры против Rapier impulse solver). Упрощённые формы не воспроизводят мелкие ветки и декорации, а урон от отдельных столкновений, анимация подъёма и сетевая репликация ragdoll ещё не реализованы. Урон от падения есть (см. ниже).

#### Высотный урон и автоматический ragdoll
- `src/fall-damage.js:createFallTracker` сохраняет пиковую world-Y между отрывом от опоры и приземлением; `src/physics.js` отдаёт трекеру фактическую высоту контакта, вычисленную через Collision World, и отрицательную скорость до её обнуления. Таблица: `h < 3` → 0, `3 ≤ h < 4` → 2 сердца, `4 ≤ h < 5` → 3, `h ≥ 5` → 5 (мгновенная смерть при полном здоровье). До следующего падения урон не повторяется: трекер блокирует повторные контакты той же ragdoll-фазы, даже если Rapier отскочит вверх; блокировка снимается только после возврата к обычному заземлённому состоянию. Если Space восстанавливает куклу **до первого контакта**, прежний пик высоты сохраняется.
- `src/player.js` забирает событие после синхронизации актёра и передаёт в `applyFallImpact`; в offline `src/vitals-ui.js:damage` обновляет чистую модель жизненных показателей, HUD, сохранение и вызывает единый `deathSystem.onDeath` при 0 HP. Если жизнь осталась — `ragdollControls.ragdoll({impactSpeed})`, без второй анимационной системы. Если в воздухе пользователь включил ragdoll самостоятельно, `observeRagdoll` дожидается контакта физического таза с общей опорой и применяет тот же урон; сон и респавн обнуляют трекер. При приземлении обычный контроллер уже установил вертикальную скорость в 0: `ragdollActivationMotion` не передаёт прошлую скорость удара повторно в Rapier (иначе решатель контактов катапультирует куклу из земли). Движение в воздухе по-прежнему наследует фактическую вертикальную скорость. Импульс заваливания при приземлении уменьшен.
- В online урон вычисляет **сервер**, а не присланный клиентом damage: `forest_server.py:record_fall_landing` отслеживает принятые пакеты `move` и посылает `vitals_state` + `fall_impact`, вызывающий физический ragdoll у клиента. Летальный удар идёт через штатный серверный `handle_death`, выпадение вещей и `player_respawn`. Ограничение: manual ragdoll не реплицирует положение тела, поэтому падение уже внутри локального online ragdoll сервер пока не видит и не наносит урон.

#### Жизненный цикл смерти
- `src/death.js` хранит phase `alive → falling → ready → alive` и управляет `src/death-screen.js`. Первый этап длится ровно 5000 мс по monotonic clock и защищает экран от ввода; fade после этого создаёт визуальную паузу с «УМЕР» и кнопкой возрождения. Игровой renderer продолжает обновляться, физика Ragdoll живёт только на время смерти.
- В offline утраченные предметы и маркер фиксируются сразу, но здоровье=0 и координаты смерти сохраняются до нажатия. Сохранение при перезагрузке восстанавливает `pending` и экран; респавн по нажатию восстанавливает витальные параметры и сохраняет новое состояние. В online сервер автоматически выставляет новые координаты/инвентарь/витальные параметры (протокол не меняется), но клиент держит собственную сцену смерти до нажатия; движение по WebSocket подавлено до перехода.


#### Добровольный ragdoll и сон
- `src/ragdoll-controls.js` создаёт общую кнопку Ragdoll (размещена справа над обычными игровыми кнопками), управляет режимами `none | manual | sleep`, подавляет второй запуск во время загрузки WASM. `controls.js` сначала предлагает `getUp()` при Space / мобильном Jump, затем вызывает настоящий `requestJump` только если игрок не лежит. В смертельном состоянии вставание запрещено.
- `camp-structures.activate(bed)` вызывает `sleepInBed` вместо непосредственного назначения кровати. Bed rest pose ориентирует скелет на спину головой к подушке и создаёт fixed mattress collider, соблюдая `orientation`. Успешное создание ragdoll затем вызывает `deathSystem.setBed` (авторитетный offline/online сценарий прежний). Поворот и перемещение персонажа возвращаются при `getUp()`, позиция у изножья в offline. В online координаты не телепортируются (сервер не умеет авторитетный сон), локально анимируется только GLB на кровати.
- Ручной ragdoll и сон выполняются только на локальной модели. Рассылка ragdoll pose в сетевой игре не реализована; другие игроки увидят стандартную позицию. Переход на реальную смерть очищает ручной режим, при этом смертельная блокировка ввода сохраняется.

### Контактный кадр рубки (Chop2, 2026-11-02)

`src/chop-timing.js` задаёт `CHOP_CONTACT_FRAME=18`, `CHOP_SOURCE_FPS=24`, `CHOP_CONTACT_CLIP_TIME=17/24` (Blender frame1/GLB time0); таймкод подтверждён по существующему `lumberjack.glb` (Chop2 имеет 44 ключа с шагом 1/24 сек, длительность 1.7917 сек). `src/chopping.js:chop` ставит `pendingSwing` без фиксирования цели и запускает `actorChop`; никаких изменений HP и FX на клике. `tickImpact(now)` выполняется из `src/player.js` после `ctx.tickActor()` и после обновления камеры, когда `action.time>=17/24`, **один раз** получает `aimed()` и выбирает любое дерево под прицелом на момент контакта, расходует `vitals.hit` и применяет урон, щепки/звук. Если персонаж перешёл в ragdoll/смерть или цель потеряна, pending отменяется. В случае отсутствия GLB используется fallback по времени и фактической скорости воспроизведения. `src/animations.js:actorChop` теперь учитывает `axe.speed`, а переход из `Chop2` в обычные движения зависит от времени AnimationMixer, а не стенового таймера.

Сетевая авторитетность сохраняется: клиент посылает `type:'hit'` только на контактном кадре, HP на клиенте обновляется по авторитетному серверному событию. В этот момент локально показываются щепки; сервер в `tree_hit` добавляет совместимое необязательное поле `by` и уже имевшееся `tree_fell.by` позволяет `src/multiplayer.js` подавить повторные локальные щепки. Боты и старые клиенты продолжают работать: `by` — дополнительное поле. Регрессии: `tests/chop-timing.test.mjs`, `tests/hit-effects.test.mjs`, `tests/multiplayer-ui.test.mjs`, `tests/test_world.py`.

**Коррекция прицеливания на 18-м кадре:** после изменения механики цель **не запоминается** в `pendingSwing`. При замахе в пустоту игрок может перевести прицел на дерево до контакта; при замахе на A можно перенести прицел на B — попадание получит B. Если на кадре 18 дерево отсутствует под прицелом, считается промах без урона, звука, щепок и расхода стамины. В `tests/hit-effects.test.mjs` проверены пустота→дерево, A→B, промах, офлайн и онлайн.

### Синхронизация физического падения дерева с SFX

Исходный `tree_fall.mp3` 9–15 с длился 6 с, а дерево достигало горизонтального положения за 1.8 с и исчезало через 2.5 с. После согласованного изменения клип регенерируется через `scripts/prepare_chopping_sounds.py` из оригинала `choppingtree.ogg` 10–15 с с фильтром `atempo=1.3` и мягкими fade — ~3.850 с в MP3. Параметры и расчётная длительность `(15-10)/1.3 ≈ 3.84615 с` сохранены в `assets/audio/metadata/CHOP_CUTS.json`. `src/fallen-log-layout.js:FALL_DURATION` и `forest_server.py:FALL_DURATION` синхронно равны 5/1.3 (подбор брёвен на сервере раньше не разблокируется). `src/falling-trees.js:tickFallingTrees` обновляет угол `a²*(π/2)`, где `a=elapsed/FALL_DURATION`, и раскрывает три бревна после полного падения. `src/player.js` передаёт падению не ограниченный физикой `dt≤.05`, а фактический wall-clock delta. `src/game-audio.js` воспроизводит `treeFall` с `pitch:1`, иначе случайная вариация скорости разрушала бы синхронизацию. Затрагивает локальное дерево и удалённые `tree_fell` события; сервер при развёртывании необходимо перезапустить.

### Предварительная подготовка и моментальное отображение брёвен

**Источник задержки:** `src/ground-boxes.js:tick()` собирает InstancedMesh коробок/брёвен по пространственным ячейкам только с интервалом 500 мс. Когда `src/falling-trees.js` удалял упавшее дерево и вызывал `revealTree()`, запись брёвен становилась доступной для подбора немедленно, но видимые меши появлялись лишь в следующем батче (задержка до 500 мс).

**Решение без лишних draw calls в обычном режиме:** `createGroundBoxes` при `add(fallen_logs pending)` заранее готовит один временный скрытый `InstancedMesh` с трансформами всех трёх сегментов (map `stagedLogs`, батч основного мира по-прежнему их пропускает). На `revealTree(treeId)` логика `pending=false` и активация `stagedLogs.get(id).visible=true` выполняются синхронно с удалением дерева — в том же кадре рендера. Когда наступает очередной 500-мс `tick`, общий батч перестраивается и лишь **после** его построения временный меш удаляется, чтобы избежать мигания и постоянного одного draw call на дерево. `remove`, `clear` и повторные сетевые `box_add` корректно удаляют/пересоздают staged mesh, а незавершённое падение не даёт подбирать брёвна. Общая серверная блокировка `ready_at` осталась неизменной. Регрессионные проверки — `tests/ground-box-optimization.test.mjs` и интеграция с `tickFallingTrees`.

- Радиусы и дальность теней: физический PointLight.distance равен VisibilityDistance для обеих ламп (default 100 м), а shadow.camera.far = VisibilityDistance + 1 м. Для выбора отбрасывающих тень объектов Renderer.getPointShadowCasters использует min(light.distance, light.userData.shadowCasterRange); по умолчанию статический предел 100 м, динамический/общий 30 м ночью. Уменьшение теневого радиуса до 9 м не обрезает освещение. Статическая карта инвалидируется при изменении кастеров, высоты/дальности света, режима или мира, но не пересчитывается периодически. Код солнца и его интервалы не менялись.

- Переиспользование PointLight: единственная лампа каждого огня создаётся один раз. Меняются только visible и shadow.autoUpdate; кэшированные карты не перемещаются между огнями.

- **Независимые расстояния ламп:** campfireVisibilityDistance / torchVisibilityDistance задают PointLight.distance, campfireActivationDistance / torchActivationDistance определяют видимость единственной лампы по дистанции игрока (по 10–250 м). Все зажжённые лампы в зоне активации доступны без искусственного лимита в три источника.

- **Независимая видимость огненных теней:** ShadowVisibilityDistance костра/факела (1–100 м) определяет, как далеко от огня игрок видит снимок карты. Дневные/ночные радиусы 1–30 м ограничивают caster-объекты (деревья, предметы, персонажи) в единственной карте. При потере live-слота последний кадр сохраняется без очистки.

- **Обновления против видимости теней:** fireShadowLimit (0–4) ограничивает только число карт, обновляемых каждый кадр, у ближних огней. Все источники внутри ShadowVisibilityDistance используют свои кэшированные тени независимо от лимита, включая значение 0 и приближение вплотную. Когда источник теряет слот, его shadow.autoUpdate отключается, но последний снимок (включая возможную тень игрока) остаётся без пересчёта. При возвращении обновления возобновляются. Ограничение в три активные построенные PointLight снято, чтобы четвёртый костёр тоже освещал и показывал тени. При большом количестве ламп стоимость обычного освещения и памяти теней выше. Чтобы отключить все огненные тени, используйте fireShadows=false.

- **Огненные тени круглосуточно:** fireShadowPolicy разрешает карты днём, ночью и в сумерках. Для костра/факела DayIntensity/NightIntensity и DayRadius/NightRadius плавно смешиваются, а единственная кубическая карта включает статические объекты и персонажей одновременно. Кэширование и независимые расстояния сохраняются; Low и fireShadows=false отключают тени. Солнце регулируется CSM отдельно.

- **Солнечный CSM:** две directional-лампы sun (far) и nearSun (near), по одной общей карте для всех caster-объектов. Нет дополнительного directional-света для игроков и нет множителя 0.5. Shader смешивает вклад без удвоения яркости. Центры карт стабилизированы texel-snapping. Дальняя карта охватывает 60–350 м (default 150), может обновляться раз в 0–20 с (default 2); при существенном перемещении игрока — чаще. Дальние casters набираются за пределами ближней зоны, включая ограниченный набор LOD-секторов дальнего леса.

Каждая карта включает и статические, и движущиеся объекты; смена Three.js r170 требует проверки shader-патча.

### Mobile HUD
`mobile-hud.css` подключён обоими HTML entrypoint; mobile/coarse overrides задают общую компоновку динамических HUD-панелей. `mobile-hud.js` инициализируется после controls и вызывает существующие кнопки через меню ⋮, не дублируя игровую логику. `touch-input.js` публикует `data-active` для видимости джойстика. `player.js` добавляет 2.5 м к плечу камеры на мобильном экране или coarse pointer, сохраняя spring-arm коллизии.

Общие правила `mobile-hud.css` применяют меню ⋮, круглую карту, сумку-иконку и fade джойстика независимо от viewport; media rules задают компактные размеры. `settings.showTouchControls` хранится в существующем settings JSON, `reflect()` синхронизирует body class и событие `forest-touch-controls`; controls сбрасывает активный джойстик при выключении.

Кнопка «FPS / диагностика» в меню ⋮ вызывает settings.setShowFps: единый showFps управляет sampling, hidden-атрибутом и сохранённым предпочтением на всех экранах. Media rules меняют только положение оверлея.

### Курицы: модель, состояние и сетевой контракт

`hens.js` загружает отдельный `assets/models/hen.glb` после входа в мир. Каждый
экземпляр имеет собственный скелет/AnimationMixer, разделяя геометрию и материалы.
Исходный персонаж высотой около 2,08 м отображается с масштабом 0,4 (около 0,83 м).
Горизонтальные Root-треки извлекаются из клипов и обнуляются в скелетной позе;
playback определяется фактической скоростью и масштабированной длиной шага.
Начальный временной сдвиг экспорта Blender удаляется. Peck-вариант проигрывается
целиком до следующего решения AI; тревога и смерть могут его прервать.

Offline-модель `hen-rules.js` не зависит от Three.js. Дополнительное необязательное
поле `hens` сохраняет животных, добычу и часы в текущем слоте; ограниченный
массив визуальных поз позволяет восстановить уже упавшие тела без нового падения. Часы поведения
отделены от часов возрождения; выключение смены суток останавливает только
трёхдневный таймер. Старые сохранения без поля остаются читаемыми.

Online-модель `hen_world.py` симулируется сервером. `hens_state` передаёт ближайшие
записи с `id,x,y,z,yaw,vx,vz,state,state_start` и `server_time`; мёртвые также
содержат `dead_at`, `respawn_at`, `loot`. Состояния движения совпадают с именами
GLB-клипов; смерть обозначена `dead`. Клиент посылает `hen_hit:{id}` и
`hen_take:{id,item,count?}`; отсутствие count означает весь остаток данного
предмета. Сервер проверяет цель, расстояние, препятствия, топор/выносливость и
вместимость, затем обновляет обычный `inventory_state`. Добыча генерируется
при смерти, повторные запросы её не создают. Поза ragdoll остаётся клиентской;
источник и его новое поколение имеют разные ID.

`hen-ragdoll.js` задаёт птичьи динамические тела и суставы, но статическое
окружение берёт из существующего `ragdoll-colliders.js` / Collision World.
Живые курицы не являются твёрдыми препятствиями для игрока. При смене мира
акторы и физические миры освобождаются, общие GPU-ресурсы не уничтожаются.

#### Общая загрузка физики и управление добычей

`rapier-loader.js` хранит один Promise импорта/инициализации Rapier для обоих
видов ragdoll. `main.js` ожидает подготовку параллельно загрузке аватара до
запуска мира; главное меню физику не загружает. Неудачная загрузка допускает
повторную попытку при активации. Физические миры по-прежнему создаются по запросу.

`hen-loot-ui.js` хранит выбор строки и обрабатывает клик/тап; `hens.js` направляет
колесо в выбор строки без освобождения pointer lock. `controls.js` направляет
E/R в открытое окно до общего подбора и строительных клавиш, включая повтор
клавиши и пустую добычу. Esc оставляет окно открытым и позволяет браузеру
освободить мышь. При смерти offline/сервер рассчитывают скорость тушки:
30% прежней скорости + 2 м/с от атакующего, с общим ограничением 3 м/с;
птичий ragdoll добавляет небольшой вертикальный импульс 0,8 м/с.


#### Суставы птицы и единый перенос добычи

`hen-ragdoll-joints.js` фиксирует Chest относительно Spine; шея/голова и ноги
используют ограниченные шарниры с упругим возвратом к позе удара. Оба локальных
joint frame привязаны к одной мировой системе, поэтому включение физики не
складывает конечности к bind pose. Head сталкивается с корпусом; перекрывающиеся
перья, ноги и соседние части корпуса не отталкивают друг друга.

Окно тушки открывает только явное взаимодействие E или touch-кнопка по подсказке.
Общий `hen-loot-actions.js` обслуживает выбор строки с клавиатуры, клики, тапы
и «забрать всё», включая проверку вместимости и стандартный `pickup`.
`pickupInteraction.interact()` при открытом окне сначала вызывает выбранную
строку и всегда поглощает действие, включая отказ и пустую добычу.
Успешный ответ `inventory_state` на `hen_take` дополнен необязательным
`hen_loot:{id,item,count}`. Клиент играет звук после принятия inventory и
совпадения receipt с ожидающим запросом; повторный ack не дублирует звук.

Физику можно проверить без браузера: установить `three@0.170.0` и
`@dimforge/rapier3d-compat@0.20.0` во временную директорию и передать путь к её
`node_modules` как `HEN_PHYSICS_NODE_MODULES` при запуске node:test.
`tests/hen-ragdoll-physics.test.mjs` использует скелет/позы игрового GLB и
настоящий Rapier, проверяя падение из Idle, Run и Peck; без зависимости этот
дополнительный физический тест пропускается, остальные тесты работают штатно.

### Общий мир мобов

Актуальная архитектура животных, будущих противников и общего инвентаря трупа
описана в [MOBS.md](MOBS.md). `mobs.js` / `mob-world.js` / `mob-population.js`
заменяют привязку runtime к курице; `hen-*` остаются совместимыми адаптерами.
Клиентские определения типов, AI, модель/варианты внешности и физический профиль
разделены. Сервер использует `MobWorld` и `MobPopulation` с реестром определений.
Старые save/ID и пакеты куриц читаются, новые клиент/сервер работают через
`mobs_state`, `mob_hit`, `mob_take` и `inventory_state.corpse_loot`.

Стайные центры и реактивное руление мобов вынесены в общие engine-neutral
модули JS/Python; настройки стаи находятся в определении типа. См. раздел
«Реактивный обход и стая» в [MOBS.md](MOBS.md).

Наведение на мобов использует `mob-targeting.js`: границы SkinnedMesh
пересчитываются после изменения позы, только для достижимых кандидатов.
Открытие трупа и локальный подбор проверяются у физического тела; подсказка
проецирует точку попадания луча. Общий `aim-state.js` отображает живую цель
красным перекрестием в обоих HTML entrypoint. Живые снимки популяций сохраняют
необязательную пару исходных координат спавна для стайного центра; старые
снимки получают её из детерминированного источника.

Ввод над окном добычи маршрутизирует `corpse-loot-pointer.js`: после обновления
камеры панель проецируется у тушки, центр экрана разрешается через DOM hit test.
UI-цель имеет приоритет над мировым прицелом, pointerdown потребляется до
запуска атаки, а отложенный контакт отменяется при наведении на панель.
Переносы предметов остаются в общем `corpse-loot-actions.js`; сеть и save
не меняются. После Esc сохраняется обычное управление DOM-кнопками.

`leave-guard.js` ставит window capture-keydown для Ctrl/Cmd+R/W на весь
игровой сеанс. Он отменяет browser default, не останавливая игровые обработчики.
В JS-полноэкранном режиме запрашивается `navigator.keyboard.lock([KeyR,KeyW])`
при поддержке API; выход из fullscreen/игры освобождает захват, поздний ответ
или отказ permission обработаны. В обычной вкладке браузер может не доставлять
Ctrl+W странице; существующий beforeunload остаётся резервным предупреждением.
