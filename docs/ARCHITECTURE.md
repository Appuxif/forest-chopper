# Forest Chopper — архитектура

> **Актуальная карта реализации (2026-11-01).** Это описание текущего кода, а не проект будущего движка.
> Для целей и правил игрового опыта см. [GAME_DESIGN.md](GAME_DESIGN.md),
> для конкретных механик — [GAME_MECHANICS_CATALOG.md](GAME_MECHANICS_CATALOG.md).
> При расхождении с этим текстом проверяйте исходники и тесты.

## 1. Система в целом

Forest Chopper — статическое веб-приложение из нативных ES-модулей JS и отдельный
Python WebSocket-сервер. Сборщик и React не требуются; Three.js и GLTFLoader
загружаются через CDN. Игрок может играть без Python-сервера (offline) или
присоединиться к общему серверному миру (online).

```text
index.html / index_debug.html
  └─ src/main-menu.js + main-menu-state.js + main-menu.css
       ├─ localStorage: метаданные сохранения, настройки, недавние серверы
       ├─ /status: разовый WebSocket-запрос, не создаёт игрока
       └─ динамический import(src/main.js) только по команде «Играть»
            ├─ Three.js: renderer / scene / camera / GLB / GPU-ресурсы
            ├─ ctx: общая точка доступа к модулям и состоянию игры
            ├─ world.js, terrain.js, distant-forest.js, micro-grass.js
            │    └─ WorldTaskScheduler → world-stream-worker.js
            ├─ player.js: requestAnimationFrame / движение / отрисовка
            ├─ controls.js, pickup-interaction.js, inventory-ui.js
            ├─ offline-save.js / progress.js / day-cycle.js
            ├─ multiplayer.js ─ WebSocket или PeerJS bridge
            │                     └─ forest_server.py (серверный мир)
            └─ world-startup.js: загрузочный overlay на этапе заполнения мира
```

Публичный `index.html` **не** создаёт `window.__gameDebug`; он доступен только
в `index_debug.html` после запуска игры. Другие точки входа — инструменты
редактирования 3D в `characters/humanoid/`, не часть главного меню.

## 2. Жизненный цикл и границы состояний

1. **Меню.** Не создаются Three.js/WebGL-контекст, игровые объекты и worker-ы.
   `src/main-menu-state.js` читает существующий offline-save, но не загружает мир.
   `src/settings.js` позволяет сохранять графические параметры до создания renderer.
2. **Выбор режима.** `continue` восстанавливает сохранение,
   `new` задаёт seed 0–999998 и сбрасывает прошлый локальный мир,
   `online` настраивает сервер/P2P. Параметры запуска передаются в
   `globalThis.__forestLaunch` с резервной записью в `sessionStorage`.
3. **Загрузка модулей.** `src/main.js` создаёт scene, renderer, общие геометрии,
   модель персонажа и игровые системы, после чего запускает frame loop.
4. **Готовность.** `src/world-startup.js` держит экран загрузки минимум 3 и
   максимум 5 секунд **после начала рендеринга**: ожидаются 5×5 ближайших
   детальных чанков (или меньшая область на Low), 3×3 тайла рельефа, начальная
   трава, первая партия дальнего леса и подключение в online. Успешная готовность
   должна стабилизироваться 350 мс. Ограничение в 5 секунд исключает зависание;
   дальние чанки могут продолжить появляться после перехода.
5. **Игра.** `src/player.js` ведёт `requestAnimationFrame`, физику, анимацию
   и кадры renderer. Мировые чанки обновляются инкрементально.
6. **Выход в меню.** Offline-save сбрасывается на диск браузера (если доступно),
   сетевой клиент отключается, затем `location.reload()`. Освобождение ресурсов
   WebGL выполняет браузер, а не сложный ручной teardown всех модулей.

Нельзя переносить создание renderer/воркеров в начальную загрузку меню:
это нарушит его лёгкую точку входа и предварительное применение MSAA.

## 4. Процедурный мир и GPU

- Мир состоит из 24-метровых детальных лесных чанков. Рельеф стримится
  более крупными тайлами (в текущем коде 96 м).
- Истинная высота грунта для коллизий вычисляется аналитически; renderer
  получает worker-сгенерированные сетки. Изменения seed/параметров должны
  отменять устаревшие результаты.
- Дальний лес объединяется в независимые 96-метровые сектора GPU Instancing;
  frustum culling выполняет Three.js.
- Трава использует отдельные near/far LOD и пул InstancedMesh.
- Пресеты графики объявлены в `src/performance-presets.js`: Ultra/High
  используют MSAA, Medium/Low — без MSAA. Изменение антиалиасинга требует
  нового WebGL-контекста; остальные поддерживаемые параметры применяются
  через настройки/пересоздание нужных батчей.
- Для геометрии и кешей действуют бюджеты; ручная проверка производительности
  на Intel iGPU/NVIDIA остаётся важной даже при зелёных unit-тестах.

Проверки перед чтением локального мира обязательны: сохранение может быть
старой версии, повреждено или недоступно из-за ограничений браузера.
**Подключение к online не перезаписывает offline-save.**
При создании нового мира сохраняются настройки и ранее открытые достижения.

## 6. Сеть: точки входа и время

- Прямое подключение к Python `websockets` по `ws://` или `wss://`
  (для страницы по HTTPS нужен WSS).
- `/status` — отдельный одноразовый WebSocket-путь: отвечает
  `server_status` с `online`, `max_players`, `world_seed`,
  `world_created_at`, `day_phase`, `protocol_version:1`; **не**
  создаёт участника и не занимает слот. На старых серверах может отсутствовать.
- `/bots` — отдельная точка для headless-ботов с собственной моделью доступа.
- Основной WebSocket начинает с `welcome`. Сервер проверяет рубку,
  сбор/подбор предметов, инвентарь, постройки, чат и общее состояние.
  Успешное действие подтверждается серверным событием; локально не следует
  оптимистично считать его завершённым.
- Рубка дерева больше не увеличивает `wood` автоматически: сервер
  сохраняет `fallen_logs` в `boxes` с `item:{id:'log',count:3}`,
  `mask:0b111`, `direction`, `tree`, `expires_at:time+3600`, отправляет
  `tree_fell` с направлением, затем `box_add`.
  Ствол становится видимым только после удаления анимированного дерева
  (`FALL_DURATION=2.5`); сервер запрещает преждевременный подбор по `ready_at`.
  `src/fallen-log-layout.js` рассчитывает постоянные центры трёх
  3,6-метровых сегментов по исходным индексам, `InstancedMesh` рисует
  только сегменты с установленными битами. `pickup_box` отправляет
  `id` контейнера **и `segment`**, сервер проверяет расстояние до
  конкретного сегмента и отдаёт одно бревно. `box_add` после успешного
  подбора содержит прежнюю геометрию, но меньшее `mask`/`count`;
  на последнем бревне — `box_remove`, плюс личный `inventory_state`. Сервер остаётся единственным арбитром при
  одновременном подборе несколькими игроками.
- `fallen_logs` и обычные выброшенные коробки имеют одинаковый TTL
  3600 секунд от создания. После истечения срока сервер удаляет связку
  целиком (`box_remove` всем клиентам), офлайн-клиент удаляет её локально.
  Подбор отдельного сегмента **не продлевает** срок остальных сегментов.
  Старые offline/server saves без `mask`/`direction` читаются с
  восстановленным непрерывным набором индексов; старый `expires_at:0`
  один раз мигрирует в TTL 1 час, сохранение сразу перезаписывается, чтобы
  перезапуск не обнулял таймер. Деревья в `felled` не восстанавливаются.
- PeerJS — сигнализация/транспортный мост, а **не** источник игрового состояния.
- Время суток: `day_phase` приходит в `welcome`, затем `time_sync`
  примерно каждые 10 секунд. Клиент экстраполирует между пакетами;
  сервер хранит абсолютную эпоху дня. Цикл — 8 минут.
- Онлайн-игрок получает своё временное состояние инвентаря/vitals;
  долговременное сохранение **общего мира** и постоянный персональный аккаунт
  — разные вещи. Системы аккаунтов в проекте нет.

Если меняется сетевой пакет, ID ресурса или save-схема — синхронизировать
Python/JS и добавить проверки совместимости.

### Коллизии создаваемых построек
- `src/structure-collisions.js` — общий слой столкновений с пользовательскими постройками. Структуры регистрируют локальные AABB-боксы в `group.userData.collisionBoxes` вместе с `collisionRadius`; они преобразуются в мировые координаты с учётом четырёх ориентаций. Не требуется физический движок и отдельное тело для каждой детали.
- `src/crafting.js` автоматически создаёт коллайдеры для всех деревянных элементов процедурной скамейки непосредственно из их реальных размеров и поворотов. Спинка и подлокотники сделаны тоньше; не добавляются «пустые» сплошные коллайдеры там, где геометрии нет. Данные не сериализуются отдельно: при загрузке offline/online мира коллайдеры восстанавливаются вместе с моделью.
- `src/physics.js`: проверка горизонтального блокирования с учётом высоты ног и головы, подшаги от туннелирования при длинном шаге, поддержка приземления на сиденье/перемещения по нему, последующего прыжка и схода, пересечения с потолком при прыжке снизу. Уже существующие коллизии установленных брёвен и скал сохранены.
- При демонтаже/удалении скамейки её коллайдер исчезает вместе с моделью. Следующие виды построек смогут подключиться к общему механизму посредством тех же данных `collisionBoxes`, без добавления отдельной системы физики.


### Два FPS-счётчика (рендер и физика)
- `src/player.js`: `animate(now)` вызывается через `requestAnimationFrame` по расписанию браузера; физика, root motion, игровые обновления и анимации выполняются перед `createFrameLimiter.allow()`. `dt=clamp((now-lastTime)/1000,0,0.05)`; отдельного fixed timestep нет.
- `src/settings.js`: `tickPhysics(now)` вызывается на каждом валидном rAF-кадре, независимо от ограничения частоты рендера; `tick(now,ctx)` считает только разрешённые кадры рендера. Оба счётчика независимо усредняются примерно раз в секунду и отображаются как `Render FPS` / `Physics FPS`.
- Фактический `Physics FPS` обычно близок к частоте обновления дисплея (60/120/144/165 Гц), но браузер может ограничивать его при нагрузке, неактивной вкладке или энергосбережении. `Render FPS` ограничивается настройкой maxFps и производительностью GPU/CPU. Сбор статистики отключён при выключенной панели и не сохраняется на сервер.


### Диагностика CPU/GPU Frame Time
- **CPU Frame Time**: `src/player.js` оборачивает весь игровой вызов `animate` замерами `performance.now()`, включая симуляцию, подготовку сцены и вызов `renderer.render()` для разрешённых рендер-кадров. На кадрах, пропущенных FPS-лимитером, измеряется только логика. `src/settings.js` усредняет все rAF-вызовы приблизительно раз в секунду. Это *wall-clock* время выполнения JS-кода, а не чистое CPU utilization (включает возможное ожидание браузера/драйвера внутри вызовов WebGL).
- **GPU Frame Time**: `src/gpu-frame-timer.js` запускает таймер `EXT_disjoint_timer_query_webgl2` (WebGL2) либо `EXT_disjoint_timer_query` (WebGL1) вокруг части `animate`, выполняющей рендеринг/теневые проходы. GPU-сэмплирование — не чаще одного запуска за 250 мс, не более одного запроса в полёте; результаты читаются исключительно при `QUERY_RESULT_AVAILABLE`, без блокирующих `gl.finish`/`readPixels`. При `GPU_DISJOINT_EXT` замер отбрасывается, при отсутствии расширения панель показывает «н/д».
- **Интерпретация**: CPU-время отображает среднее по всем rAF-циклам (включая кадры без рендера при его ограничении); GPU-время относится только к выбранным отрисованным кадрам, и эти величины не суммируются в полное время кадра. Измерения включаются только при активной FPS-панели, не изменяют ограничители и не отправляются на сервер.


### Костры, факелы и лагерь (MVP)
- `src/camp-rules.js`: декларативные рецепты и проверка структуры; `src/camp-structures.js`: 3D костра, факела, стола, ограды, верстака, интерактивная кнопка, F, 3 ближайших активных PointLight без теней (неподсвеченные объекты сохраняют пламя), единые коллайдеры с другими постройками.
- Новые структуры хранятся отдельно от `storages`: локальные `camp_structures: [{id,kind,x,z,orientation,lit}]` в том же offline save v1, серверные `camp_structures: {id:...}` в общем JSON. Отсутствующий ключ старого сохранения означает пустой список. Лимит 100, строгая валидация типов/координат. Сервер отдаёт список в `welcome`, рассылает `camp_add` при размещении и `camp_update` при переключении огня; списание ингредиентов только на сервере.
- `src/status-effects.js` и `src/vitals.js`: ограниченная по времени регенерация stamina. `vitals.effects` содержит сроки истечения в Unix seconds и безопасно обрабатывается на загрузке. Python-реализация использует те же 30 с и множитель 2, отправляет активные эффекты только в `vitals_state`. Личные состояния multiplayer не сохраняются между сессиями (как и прежде).


### Компактная книга рецептов и отображаемые имена предметов
- `src/item-display.js` — единый словарь русских имён и запасных emoji-иконок для всех игровых предметов и собираемых грибов/цветов. В инвентаре, хранилищах, подсказках подбора и книге не показываются внутренние идентификаторы вроде `flower:daisy`. Сетевой протокол и сохранения по-прежнему оперируют стабильными техническими `id`.
- `src/recipe-book-ui.js`: master/detail вместо одного рецепта на разворот. Слева список максимум 5 рецептов текущей категории, справа отдельная панель деталей выбранного рецепта с расходом ресурсов, свойствами и единственной кнопкой `Создать`/`Поставить`. Стрелки листают **пятёрки**, при смене категории/страницы выбирается первый рецепт; при обычном изменении инвентаря выбор сохраняется. На узком экране список компактной сеткой располагается сверху, детали снизу. Количество кнопок/операций при крафте не менялось, серверные проверки не обходятся.


### Строительство по 3D-сетке (2026-11-01, prototype)
- Все брёвна и сегменты упавших деревьев — **3 м** при диаметре **0,58 м**. Сетка X/Y/Z — 0,5 м.
- `R` вращает брёвна по X, Z и вертикальной Y. `PageUp/PageDown` поднимает/опускает на 0,5 м. `Alt + ←/→` сдвигает по мировой X, `Alt + ↑/↓` — по мировой Z. E/клик устанавливает. Уровней высоты 16 (0–7,5 м).
- Для построек используется только формат `{x,z,orientation,height}`; старый формат `level` аннулирован. На загрузке старые **установленные** брёвна удаляются из offline/server save, остальные части мира (инвентарь, деревья, здания) остаются. Загрузка может изменить состав сохранённых структур, возврата ресурсов за старые брёвна нет.
- `log-grid.js` — единые функции снапа, геометрии и поворота. Отдельная поддержка длинных старых строительных брёвен не нужна. Сервер отклоняет старые `place_item` без `height`.
