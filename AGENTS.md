# AGENTS.md — Forest Chopper

Инструкции для **coding-агентов**, которые разрабатывают, тестируют и улучшают Forest Chopper. Этот файл относится ко всему репозиторию. Он **не заменяет** инструкции для LLM-персонажей внутри игры.

## 1. С чего начать

1. Открой `README.md` и проверь текущее состояние через `git status --short --branch` и `git log -5 --oneline`. Не предполагай, что состояние ветки совпадает с документацией.
2. Найди относящиеся к задаче файлы. Читай только нужные участки, а не весь проект в каждый инструментальный вызов.
3. До правок запусти базовые проверки (ниже). Отдельно отмечай уже существующие ошибки.
4. Делай **самостоятельно небольшие, завершённые изменения**: разобраться → реализовать → добавить тест → проверить в браузере/на сервере → зафиксировать результат.
5. Не выдавай синтаксическую проверку за тест игрового поведения, а удачный вызов команды — за подтверждённый результат.

## 2. Продукт и стек

Forest Chopper — экспериментальная 3D browser sandbox/co-op игра: процедурный лес, рубка деревьев, добыча древесины, постройка из брёвен, физика ходьбы/прыжков, чат, миникарта и мультиплеер. Проект предназначен для быстрых экспериментов; **не превращай маленькую задачу в большой рефакторинг**.

- **Клиент:** нативные ES-модули JavaScript, Three.js/WebGL, HTML/CSS, процедурные деревья с GPU Instancing и шейдерным ветром, GLB-персонаж из Blender. **Без обязательной сборки**, React, Vite, TypeScript или нового UI-фреймворка.
- **Сервер:** Python, `websockets`; authoritative state для дерева/ресурсов/построек/чата; игроки соединяются по WebSocket, есть мост PeerJS.
- **Headless-боты:** Python-симуляция на сервере, отдельный внешний MCP/CLI gateway. Ботам **не нужен браузер или рендер**.
- **Хранилище общего мира:** `forest_world.json` на сервере. Это пользовательские данные, не тестовый fixture.

## 3. Правила реализации

- **Минимальные, понятные патчи.** Используй существующие функции, `ctx`, модули и структуры. Не добавляй архитектуру «на будущее», если конкретная задача не требует её.
- Не меняй молча сетевые сообщения, ID деревьев, формат сохранения и seed-генерацию: от этого зависят сервер, браузер и боты. Если изменение неизбежно — сохрани совместимость и добавь интеграционный тест.
- Сетевые ресурсы, рубка и постройки требуют подтверждения **сервером**; клиентское отображение и предварительная валидация не заменяют серверной проверки.
- Различай **offline** и **online**: локальные изменения не должны попадать в авторитетное состояние сетевого мира и наоборот.
- Для Three.js соблюдай жизненный цикл `Geometry`, `Material`, `Texture` и event listeners: освобождай только принадлежащие объекту ресурсы, **не dispose общие**, которыми ещё пользуются другие mesh.
- Игровая производительность важна: никаких растущих без лимита массивов частиц/объектов и лишних тяжёлых операций в каждом кадре.
- Новый UI должен работать на **desktop и touch/mobile**, не закрывать основные кнопки и учитывать reduced motion там, где есть анимационные эффекты.
- **Точка входа — главное меню:** `main-menu.js` не должен загружать Three.js/воркеры до выбора режима; `main.js` импортируется динамически. WebGL-опции должны применяться до создания renderer. Debug API доступен лишь после входа в игру.
- Для изменений в обычной игре учитывай **оба HTML entrypoint**; `debug.js` не должен утекать в обычный `index.html`.
- **Контракты:** сохраняй совместимость с payload `version:1` в `forest-chopper:slot:v1:1` … `forest-chopper:slot:v1:10`, серверным `forest_world.json`, авторитетными WS-пакетами, seed/ID деревьев; multiplayer не должен затирать offline-save.
- **Слоты:** `offline-save.js` пишет только выбранный слот (1–10), `save-slots.js` проверяет JSON-архивы. Старый ключ `forest-chopper:offline-world:v1` текущим кодом не читается и автоматически не мигрируется; не удаляй его. Параметр URL `type=new` выбирает слот 1, `type=continue` — первый валидный занятый слот. Настройки, достижения, tutorial/progress используют отдельные общие ключи, не считай их частью архива слотов. Проверки: `tests/save-slots.test.mjs`, `tests/offline-save.test.mjs`, `tests/main-menu.test.mjs`.
- **Документация в том же коммите:** обновляй `GAME_MECHANICS_CATALOG.md` при добавлении/изменении механики, `ARCHITECTURE.md` при изменении модулей/сетевого протокола/сохранений и `GAME_DESIGN.md` при изменении целевого игрового опыта. `README.md` должен соответствовать актуальным кнопкам и способу запуска.
- Не трогай headless AI/MCP/Jev ради косметического улучшения клиента. При необходимости менять протокол — сначала объясни причину тестами и минимизируй область правки.

## 4. Проверки и безопасная тестовая среда

Базовые команды из корня проекта:

```bash
git status --short --branch
node --test tests/*.test.mjs
python3 -m unittest discover -s tests -v
python3 -m py_compile forest_server.py server_bots.py bot_gateway.py bot_mcp.py bot_cli.py
for f in src/*.js; do node --check "$f" || exit 1; done
git diff --check
```

Для новой JS-логики предпочитай встроенный `node:test` (`node --test`), для сервера — `unittest`, `asyncio` и `tempfile`. Пиши **реальные assertions** на игровые сценарии, не тесты-заглушки.

Для браузерной проверки:
- Запускай **свой** локальный HTTP-сервер на свободном порту (например, `python3 -m http.server 18000 --bind 127.0.0.1`) и открывай отдельную тестовую вкладку через Chrome DevTools MCP.
- Сначала открой главное меню, выбери «Локальная игра» → занятый/пустой слот или «Мультиплеер»; `window.__gameDebug` появляется **только после** инициализации мира в `index_debug.html`. Само отсутствие debug API в меню — не ошибка.
- Для быстрых проверок используй `index_debug.html?type=continue&performance=low&diag=true`; для чистого воспроизводимого мира — `?type=new&seed=123&force=true&performance=low&diag=true` **строго в изолированном контексте**, чтобы не повредить сохранение пользователя. Для сравнения графики выбирай нужный `performance` вместо `low`. Включай `diag=true` для FPS и диагностик.
- Проверяй состояние DOM, ошибки консоли и screenshots desktop/mobile. При необходимости используй `index_debug.html` и `window.__gameDebug` **только в своей вкладке**.
- Не управляй пользовательскими/чужими вкладками и не закрывай их.
- Для multiplayer-тестов запускай **отдельный сервер и временный save**, например:

```bash
python3 forest_server.py --host 127.0.0.1 --port 18765 --save /tmp/forest-chopper-test-world.json
```

Это **только пример**: выбирай свободный порт и уникальный временный путь, не перезаписывай чужой файл в `/tmp`. Останавливай только тестовые процессы, которые сам запустил. Не тестируй разрушительные действия на публичной комнате или реальном мире.

Для каждой завершённой игровой фичи проверь соответствующую логику, визуал там, где он важен, отсутствие консольных ошибок и отсутствие регрессий. Если внешнее окружение недоступно — честно запиши непроверенные области.

## 6. Критерий «готово»

Фича считается готовой, когда она реализована **минимально и без регрессий**, имеет адекватную автоматическую проверку, работает в соответствующем режиме (online/offline), протестирована в браузере при наличии визуальных изменений, а ограничения честно описаны. **Не утверждай, что пользовательский геймплей субъективно хорош, только потому что тесты зелёные.**

При конфликте этого файла с конкретным свежим заданием пользователя выполняй задание в допустимых пределах, но сохраняй безопасность данных и существующего мира.

## Collision World — обязательное правило

При добавлении нового твёрдого объекта или новой формы коллизии обновляйте **`src/collision-world.js`**, не создавайте вторую модель геометрии в `physics.js` или `ragdoll-colliders.js`. Для построек задавайте `group.userData.collisionBoxes`, для отдельных категорий расширяйте engine-neutral генератор форм. Обычная физика работает через `src/collision-kinematic.js`, Rapier — через `src/ragdoll-colliders.js`. При создании, удалении, перемещении объектов или загрузке чанков вызывайте `ctx.collisionWorld?.invalidate?.()`, чтобы активный ragdoll обновил свои статические тела. При изменении проверяйте тесты `tests/collision-world.test.mjs`, `tests/physics.test.mjs`, `tests/ragdoll-colliders.test.mjs`.

## Высотный урон и ragdoll

Новые виды урона наносите через единые `src/vitals.js:damage` / `src/vitals-ui.js:damage`, чтобы корректно обновлялись HUD, сохранения и `deathSystem`. Высоту падения отслеживает **`src/fall-damage.js`**, а не отдельный код в анимациях или камере. Порог урона 3/4/5 м — тесты `tests/fall-damage.test.mjs` и `tests/test_fall_damage.py`; в multiplayer здоровье изменяет только `forest_server.py` на основе проверенных пакетов, клиент не должен доверять входящему damage, высоту от локального ragdoll в online сервер пока не знает. Не дублировать запуск смерти при 0 HP или запуск ragdoll после смертельного падения.

При автоматическом ragdoll после приземления **никогда не передавайте прошлую скорость удара как новую отрицательную линейную скорость**: ноги уже на опоре, движок вытолкнет капсулы и произойдёт неестественный высокий отскок. Для manual ragdoll в воздухе скорость сохраняется. Повторные отскоки одного тела нельзя считать новым падением до подъёма / заземления. Регрессии описаны в `tests/fall-damage.test.mjs` и `tests/ragdoll-motion.test.mjs`.

## Audio

Все новые звуки регистрируются в `src/sound-rules.js` (`AUDIO_FILES` и `SOUND_CONTROLS`). Только `src/game-audio.js` работает с AudioContext и буферами; игровые модули вызывают `ctx.audio?.effect(...)`/`ctx.audio?.hurt(...)`. Не создавать новый AudioContext/HTMLAudioElement в отдельных системах. Загрузка аудио только после первого взаимодействия пользователя; внешний CDN для звуков запрещён. Хранить лицензии и авторов в `assets/audio/ATTRIBUTION.md`, особенно **CC BY 4.0** для Nature Ambient Pack и Cozy Farm SFX, **CC BY 3.0** для сверчков и `chopping-tree`. Регрессии — `tests/sound-rules.test.mjs`, `tests/game-audio.test.mjs`, `tests/settings.test.mjs`.

Для голосов боли и смерти использовать только `VOICE_VARIANTS` в `src/sound-rules.js`, не создавать магические имена аудиофайлов в геймплейных модулях. `deathSystem.begin()` запускает **отдельный** голос смерти, а `vitals` при смерти (0 HP) не должен одновременно проигрывать обычный стон. Женские фрагменты `Female Gruntwork - 1` отобраны пользователем: **только** `hurt_female_{3,4,5,20}` и `jump_female_{24,25,26,27,28}`. Остальные отклонены и не должны регенерироваться. Мужские прыжки — обе записи `JumpSoundsMan.zip` (IgnasD, CC0). Их интервалы и ID лежат в `assets/audio/metadata/VOICE_CUTS.json`, а скрипт воспроизведения — в `scripts/prepare_voice_sounds.py`. Условия лицензирования **CC BY-SA 3.0/4.0** — в атрибуции; не терять её при упаковке.

При изменении рубки: исходник `choppingtree.ogg` (kurt, CC BY 3.0), утверждённые интервалы падения дерева **10–15 с, ускорение ×1.3**, ударов **16–25 с**; нарезка через `scripts/prepare_chopping_sounds.py`, спецификация `assets/audio/metadata/CHOP_CUTS.json`, рантайм-каталог `AXE_VARIANTS`. Не возвращать отклонённые `axe_hit_1`/`axe_hoe_*` и `owl` в микшер, настройки или assets без нового запроса.

Дефект звуков рубки (проверено 2026-11-02): silencedetect с неверными интервалами 16.29–17.67 с вырезал почти тишину. Нельзя принимать тишину за удар: используйте PCM огибающую, проверяйте расположение пиков и хвост, а не только silence boundaries. Утверждённая повторная нарезка — семь ударов 18.12–24.0 с в `scripts/prepare_chopping_sounds.py`. `step_grass_cozy` исключён: на траве **только** `step_leaves_1/2`.

Реверс `pickup` для **ручного выбрасывания** стака из инвентаря: `drop.mp3` и `src/ground-boxes.js:dropSlot`. Звук строго не переносить в общий `groundBoxes.add`, потому что этот же метод используется для автоматических коробок при смерти. Регенерация: `scripts/prepare_drop_sound.py`; лицензия производного эффекта CC BY 4.0 в `assets/audio/ATTRIBUTION.md`.

После реорганизации `assets/audio` все новые MP3 размещаются в тематической папке, а не в корне. Источник истины — `AUDIO_FILES` из `src/sound-rules.js`: имена — стабильные логические ID, значения — относительные пути (`chopping/axe_chop_1.mp3` и т.п.). Генераторы обязаны сохранять аудио сразу в нужные подкаталоги и таймкоды в `assets/audio/metadata/`. Схема — `assets/audio/README.md`; регрессионный тест проверяет, что каталог и зарегистрированные файлы совпадают, без неиспользуемых MP3.

Jump SFX вызывается только внутри `src/physics.js:requestJump` **после** успешного расхода выносливости и проверки земли (`ctx.audio?.jump()`). Не запускать звук в общем обработчике Space/pointerdown, в `simulateVertical` или при ragdoll getUp. Для прыжков существуют `jumpMale/jumpFemale` в `SOUND_CONTROLS`, отдельные от боли и смерти.

Удары по дереву строго синхронизируются с **18-м кадром Chop2** (`src/chop-timing.js`: 17/24 секунды в клипе) по **AnimationAction.time**, а не setTimeout или FPS рендера. Ввод начинает замах; `tickImpact` в цикле после mixer.update и обновления камеры определяет дерево строго по текущему прицелу на контактном кадре, без фиксации цели от клика (разрешены A→B и пустота→B). Только на контакте расходуется stamina, изменяется HP, включается звук и появляются щепки. При смерти/ragdoll промах отменяет удар. Онлайн: сервер подтверждает HP, локальные щепки показываются на контакте, `tree_hit.by` не даёт повторов при ack. Не возвращать мгновенный урон на onclick и не переносить проверку контакта перед `tickActor`.

Длительность **падения дерева** связана со звуком: `assets/audio/chopping/tree_fall.mp3` создаётся из 10–15 с исходной дорожки с `atempo=1.3`, значит `FALL_DURATION=5/1.3` сек в `src/fallen-log-layout.js` и `forest_server.py`. `src/falling-trees.js` обязан наклонять дерево до этого момента, а не до старых 1.8 с, и открывать доступ к брёвнам только в конце. `src/player.js` передаёт wall-clock delta без cap .05 для падения; `src/game-audio.js` должен использовать фиксированный pitch 1. При изменениях обязательно обновлять и проверять метаданные `assets/audio/metadata/CHOP_CUTS.json`, длительность MP3 и оба Fall Duration; сервер перезапускать.

**Появление брёвен без задержки:** `groundBoxes` батчит видимые контейнеры каждые 500 мс, поэтому для `fallen_logs` с флагом `pending` нужно заранее подготавливать скрытый `InstancedMesh` в `stagedLogs`. `revealTree(id)` включает его **синхронно** с исчезновением дерева; на следующем батч-тике меш заменяется общей геометрией, только после этого временный удаляется. Не переносить появление бревен на очередной `groundBoxes.tick`, иначе вернётся задержка ~0.5 с. Не нарушать `pending` для клиентского подбора и серверное `ready_at` для сетевого. Lifecycle `remove/clear/box_add` должен чистить staged meshes; проверять `tests/ground-box-optimization.test.mjs`.

## Мобы и общий инвентарь трупа

Текущая архитектура — [docs/MOBS.md](docs/MOBS.md). Используйте `ctx.mobs`,
реестры типов/поведения, общие `mob-world` / `mob-population`, `mob-ragdoll`
и `corpse-loot-*`. `hen-*` и `ctx.hens` — адаптеры старых импортов и сохранений,
не основа для копирования нового существа. Категория/подкатегория внешности,
фракция, AI, характеристики и физический профиль — разные параметры. Новое
существо не должно создавать вторую модель геометрии, собственный микшер
аудио или копию жизненного цикла смерти игрока. Для изменения формата мобов
сохраняйте старые ID/снимки и проверяйте оба языка, несколько типов и WS.
